## Estratégia Multi-Tenant

**Modelo adotado: Shared Schema com Discriminador por Coluna**

Todas as tabelas de negócio possuem a coluna `empresa_id UUID` que identifica o tenant owner.
Não existe schema separado por tenant. Toda a isolação ocorre via filtro na aplicação.

### Por que esta escolha?
- Simplicidade operacional (1 banco, 1 schema)
- Supabase gerencia auth + RLS natively
- Escala bem para dezenas/centenas de empresas

### Como funciona o isolamento?

```
1. Request chega com Bearer JWT (Supabase)
2. TenantFilter extrai sub (user UUID) do token validado
3. TenantResolver consulta: SELECT empresa_id FROM usuarios_empresa WHERE user_id = :userId
4. empresa_id é armazenado em TenantContext (ThreadLocal)
5. Cada método de serviço lê TenantContext.getRequiredEmpresaId() e filtra queries
6. TenantFilter.finally() executa TenantContext.clear() ao fim da request
```

## Tabelas

### `empresas` — Tenants do SaaS
```sql
CREATE TABLE empresas (
    id          uuid DEFAULT gen_random_uuid() PRIMARY KEY,
    nome        varchar NOT NULL,
    email       varchar UNIQUE NOT NULL,
    plano       varchar DEFAULT 'basico' CHECK (plano IN ('basico','profissional','enterprise')),
    ativo       boolean DEFAULT true,
    created_at  timestamptz DEFAULT now()
);
-- Comentários: "Tenants do SaaS — cada empresa cliente"
-- RLS: habilitado
```

### `usuarios_empresa` — Vínculo Usuário ↔ Empresa
```sql
CREATE TABLE usuarios_empresa (
    id          uuid DEFAULT gen_random_uuid() PRIMARY KEY,
    empresa_id  uuid NOT NULL REFERENCES empresas(id),
    user_id     uuid NOT NULL REFERENCES auth.users(id),
    role        varchar DEFAULT 'operador' CHECK (role IN ('admin','operador','visualizador')),
    created_at  timestamptz DEFAULT now()
);
-- Comentários: "Vínculo usuário ↔ empresa com role de acesso"
-- RLS: habilitado
```

### `clientes` — Clientes de cada Empresa
```sql
CREATE TABLE clientes (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id  uuid REFERENCES empresas(id),        -- tenant owner
    user_id     uuid DEFAULT auth.uid() REFERENCES auth.users(id), -- LEGADO C# (não usar)
    nome        varchar NOT NULL CHECK (char_length(TRIM(nome)) > 0),
    email       varchar,
    telefone    varchar,
    endereco    varchar,
    created_at  timestamptz DEFAULT now()
);
-- RLS: habilitado
-- NOTA: user_id é coluna legada do C# (user_id por linha). No Java, o isolamento é via empresa_id.
```

### `produtos` — Produtos à Venda
```sql
CREATE TABLE produtos (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id  uuid REFERENCES empresas(id),
    nome        varchar NOT NULL,
    preco       numeric,
    custo       numeric,
    ativo       boolean,
    receita_id  bigint REFERENCES receitas(id),       -- nullable: produto pode não ter receita
    created_at  timestamptz DEFAULT now()
);
-- RLS: habilitado
-- FK: receita_id pode ser NULL (produto simples)
```

### `receitas` — Receitas de Produtos
```sql
CREATE TABLE receitas (
    id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id    uuid REFERENCES empresas(id),
    nome          varchar DEFAULT '',
    modo_preparo  text DEFAULT '',
    created_at    timestamptz DEFAULT now()
);
-- RLS: habilitado
```

### `receitaIngredientes` — Ingredientes de Receitas
```sql
CREATE TABLE "receitaIngredientes" (  -- atenção: camelCase, precisa de aspas no SQL
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id  uuid REFERENCES empresas(id),
    receita_id  bigint REFERENCES receitas(id),
    nome        varchar NOT NULL,
    quantidade  numeric NOT NULL,
    unidade     text NOT NULL
);
-- RLS: habilitado
-- DÍVIDA TÉCNICA: nome da tabela em camelCase (única anomalia). Java usa backtick: @Table(name = "`receitaIngredientes`")
```

### `ingredientes_insumo` — Mapeamento Ingrediente → Insumo
```sql
CREATE TABLE ingredientes_insumo (
    id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id      uuid REFERENCES empresas(id),
    ingrediente_id  bigint NOT NULL REFERENCES "receitaIngredientes"(id),
    insumo_id       bigint NOT NULL REFERENCES insumos(id),
    fator_conversao numeric DEFAULT 1
);
-- RLS: habilitado
-- OneToOne com receitaIngredientes (ingrediente só pode ter 1 mapeamento)
```

### `insumos` — Itens de Estoque
```sql
CREATE TABLE insumos (
    id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id      uuid REFERENCES empresas(id),
    nome            varchar DEFAULT '',
    quantidade      numeric NOT NULL,
    unidade         varchar DEFAULT '',
    validade        date,
    estoque_minimo  numeric,
    status          varchar,                           -- calculado pela aplicação
    created_at      timestamp DEFAULT now()            -- SEM timezone (inconsistência!)
);
-- RLS: habilitado
-- DÍVIDA TÉCNICA: created_at é timestamp (sem timezone) enquanto todas as outras tabelas usam timestamptz
```

### `pedidos` — Pedidos
```sql
CREATE TABLE pedidos (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id  uuid REFERENCES empresas(id),
    cliente_id  bigint REFERENCES clientes(id),       -- nullable: pedido anônimo
    data        timestamptz DEFAULT now(),             -- ATENÇÃO: "data" é palavra reservada em alguns contextos
    valor       numeric NOT NULL,
    status      varchar,                               -- Pendente | Em Preparo | Em Rota de Entrega | Entregue
    observacoes text
);
-- RLS: habilitado
```

### `pedidoprodutos` — Produtos de um Pedido (N:N)
```sql
CREATE TABLE pedidoprodutos (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    empresa_id  uuid REFERENCES empresas(id),
    pedido_id   bigint REFERENCES pedidos(id),
    produto_id  bigint REFERENCES produtos(id),
    quantidade  smallint
);
-- RLS: habilitado
-- NOTA: empresa_id aqui serve para isolamento; poderia ser derivado via pedido_id
```

## Convenções de Nomenclatura

| Regra | Exemplo |
|---|---|
| Tabelas em snake_case | `pedido_produtos`, `ingredientes_insumo` |
| **Exceção:** `receitaIngredientes` camelCase | Anomalia histórica — manter compatibilidade |
| PKs sempre `id` bigint identity | `id bigint GENERATED BY DEFAULT AS IDENTITY` |
| FKs no padrão `<entidade>_id` | `empresa_id`, `receita_id`, `cliente_id` |
| Tenant discriminador sempre `empresa_id uuid` | Toda tabela de negócio tem esta coluna |
| Timestamps `created_at` com timezone | `timestamptz DEFAULT now()` |
| **Exceção:** `insumos.created_at` sem timezone | Anomalia histórica — corrigir em migration futura |

## RLS (Row Level Security)

RLS está **habilitado** em todas as tabelas. No entanto, o backend Spring Boot conecta com as
credenciais de `DB_USERNAME` (dono do banco / service role), que tem acesso irrestrito.

O isolamento real é feito na camada de aplicação via `TenantContext`.

O RLS serve como **segunda linha de defesa** — se a aplicação falhar em filtrar, o banco bloqueia.

Policies existem mas são gerenciadas via Supabase. O backend Java não depende das policies RLS
para funcionar corretamente — ele garante o isolamento antes.

## Migrações

O schema foi criado via **Supabase MCP** (migrations 001–006) antes da criação do projeto Java.
O Flyway está configurado com `baseline-on-migrate=true, baseline-version=1` para não tentar
rodar migrações em cima de um banco já existente.

Scripts de migration para novas alterações devem ficar em:
```
backend/src/main/resources/db/migration/V2__<descricao>.sql
backend/src/main/resources/db/migration/V3__<descricao>.sql
...
```

## Notas de Compatibilidade C# → Java

| Aspecto | C# | Java |
|---|---|---|
| PKs | `int` (32-bit) | `Long` (64-bit) — `bigint` no banco |
| Tenant | `user_id` por linha | `empresa_id` por linha |
| Auth | Sem autenticação real | Bearer JWT Supabase |
| Queries | Entity Framework, sem filtro tenant | JPA + filtro `empresa_id` obrigatório |
| Tabela pedidos | `Table("pedidos")` | `Table("pedidos")` — mesma |
| Tabela junção pedido | `Table("pedidoprodutos")` | `Table("pedidoprodutos")` — mesma |
